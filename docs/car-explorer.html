2.2udev 规则原文

两个 CP2102 芯片型号完全相同，只能靠出厂序列号区分，这就是为什么规则必须写 ATTRS{serial} 而不能只写 vendor/product。

KERNEL=="ttyUSB*", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", ATTRS{serial}=="0002", SYMLINK+="wheeltec_controller"
KERNEL=="ttyUSB*", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", ATTRS{serial}=="0001", SYMLINK+="wheeltec_laser"
KERNEL=="ttyUSB*", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", ATTRS{serial}=="0003", SYMLINK+="wheeltec_laser"   # LD14 型号兼容
KERNEL=="ttyCH343USB*", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", ATTRS{serial}=="0002", SYMLINK+="wheeltec_controller"

2.3容器边界

宿主机（Debian 12 / aarch64）

  • udev 生成 /dev/wheeltec_*
  • Docker 引擎管理容器 codex-camera-live
  • systemd user unit 拉起网页控制台

容器内（Ubuntu 22.04.4 + Humble）

  • 只有通过 --device=/dev/wheeltec_controller --device=/dev/wheeltec_laser 挂进来的节点才可见
  • ROS2 话题、lslidar_driver、turn_on_wheeltec_robot 都跑在这里
  • 发布 /scan /odom /PowerVoltage，订阅 /cmd_vel

这也是「ROS2 只在容器里」的由来：宿主机上没有 ROS 环境，任何 ros2 topic list 都得先 docker exec 进去再 source——这是第 07 节里「启动脚本不检查失败」那条缺陷的直接温床。

车上的逻辑是「感知 → 识别 → 会话状态机 → 规划 → 执行 → 反馈」六段式。下面数字全部来自 2026-11-16 的在线快照，不是设计目标。

6.1BOM 估算

套件口径

整车 ¥1,149 是整机套餐价，已经把底盘、主控、麦轮、计算板、电池、线束打包。单独按散件复算会明显更贵——因为散件要另买线缆、支架、电源。

若按散件重造（人民币，粗估）

  • 底盘 + 麦轮 + 电机：¥600 – 800
  • C30D 主控板：¥340
  • Pi 5 4 GB：¥600 – 750
  • N10 雷达：¥479
  • 深度相机：¥400 – 900（二手/库存）
  • 电池 + 线束 + 结构件：¥300 – 500
  • 合计约 ¥2,700 – 3,800

结论：买套件比散件便宜约四成，主要省在结构件、线束和整机调试成本上。这也是教学机型能压到千元级的原因。

6.2停产带来的风险

Astra S 已停产意味着：一旦这台坏掉，无法买到同型号原厂新件。换 Astra 2 / Gemini 2 后，驱动、分辨率、内参、帧率都会变，calibration.json 里的 camera_to_front_m 和相机内参都要重标——这不是换一个零件，是换一条感知链路。

每条都带 文件:行号，可以直接在仓库里跳过去核对。按「会不会伤人 / 会不会静默失效 / 只是不优雅」分三级。

7.1安全级（P0）

P0

关机令牌在 /status 里明文广播

src/camera_viewer.py

启动时生成的会话令牌，被当作 start_status 的一部分随 GET /status 一起返回。而同一个令牌正是 POST /shutdown 的校验凭据——谁能读状态，谁就能关机，凭据与公告合一。

:69 START_SESSION = secrets.token_hex(8) :546 events=list(session.events)[-10:], start_status=[START_SESSION, now, start_generation]) :448 ... data.get('boot_id') != START_SESSION: :476 subprocess.run(['sudo', '-n', 'systemctl', 'poweroff'], check=True, timeout=3)
工业做法
密钥/令牌永不出现在任何可读端点；关机是带外操作或双人确认，且需审计留痕。
迁移动作
把令牌从 /status 移除；/shutdown 改为独立鉴权 + 二次确认 + 审计日志。
P0

没有硬件急停，只有软件看门狗

follow_actuator · STOP_BURST_S

全部「停」的能力都依赖软件：/cmd_vel 归零、280 ms 看门狗、STOP_BURST_S=1.5 的零速突发。一旦进程死锁、Docker 卡住或 USB 掉线，没有任何独立通路能切断电机动力。

src/follow_actuator.py:25 STOP_BURST_S = 1.5 src/follow_actuator.py:38 self.create_timer(0.05, self.tick)
工业做法
独立双通道 E-stop，直接断动力或短接刹车；符合 ISO 13849 PL c / Cat 2，安全功能与控制软件物理隔离。
迁移动作
加一个物理急停按钮接底盘使能；安全回路不经过 Pi 与容器。
P0

制动减速度是假设值，却用于安全距离计算

config/follow_settings.json

braking_verified=false 而 brake_deceleration_mps2=0.30 已被用于「按速度与制动余量停车」。等于用一个从未实测的数决定停不停得下来。calibration.json 里 stop_tests_completed: 0、brake_tests_completed: 0。

"braking_verified": false, "brake_deceleration_mps2": 0.30, "stop_tests_completed": 0, "brake_tests_completed": 0
工业做法
制动性能必须实测标定（不同载重/地面），并留安全系数；未标定时应把速度压到保守值并显式告警。
迁移动作
做斜坡制动试验，标定实际减速度；标定前锁定更低速度上限。
P0

控制周期里同步做 HTTP，抖动直冲看门狗预算

src/camera_viewer.py:142-161

控制循环在 motion_lock 内调用 publish_actuator_command，而它是一次跨进程 HTTP（超时 0.22 s）。实测最慢 333 ms 已超过 280 ms 看门狗预算，余量只剩约 0 ms。

:65 CONTROL_TIMEOUT = 0.22 :142 with motion_lock: :155 publish_actuator_command(active, ...) 实测：看门狗 10 次最慢 333.38 ms vs 预算 280 ms
工业做法
控制回路内不做网络/磁盘 I/O；实时线程与 IO 线程通过无锁队列解耦，周期抖动有硬上界。
迁移动作
改成进程内发布或异步队列；把 HTTP 移出控制路径。
P0

/status 是「上帝端点」，无分级

camera_viewer.py 路由

状态、事件、令牌、性能数据全塞在一个 GET 里，无鉴权分层。HMI、监控、运维共用同一出口，任何一方被攻破即等于拿到控制面。

工业做法
控制面与观测面分离；控制接口要求强鉴权与审计，观测接口只读且脱敏。
迁移动作
拆分 /status 与 /control，前者脱敏只读。

7.2架构级（P1）

P1

用 Flask HTTP 桥架空了 ROS2

src/follow_actuator.py · src/follow_sensors.py

系统名义上跑 ROS2，实际上用 18767/18768 两个 Flask 端口把话题转成 JSON 轮询。结果是丢掉了 ROS2 最值钱的东西：QoS、transient-local、message_filters 时间同步、lifecycle、composition。/cmd_vel 还是裸数字 QoS（10）。

src/follow_actuator.py:32 self.publisher = self.create_publisher(Twist, "/cmd_vel", 10) src/follow_actuator.py:44 self.create_subscription(Float32, "/PowerVoltage", ...)
工业做法
节点间直接走 DDS，显式声明 QoS（传感器用 SensorDataQoS，控制用可靠有序），时间同步用 message_filters。
迁移动作
删掉 HTTP 桥，改成原生节点 / 组件；QoS 显式化。
P1

两套规划器并存，其中一套是死代码

src/follow_control.py:292 / :320

plan_visual_follow 与 plan_follow 零调用者。现役规划在 follow_motion.py 的 FollowMotion.plan()，由 follow_session.py:126 调用。两套逻辑并存 = 改一处参数另一处不生效，后来人极易改错文件。

src/follow_session.py:8 from follow_motion import FollowMotion src/follow_session.py:126 plan = self.motion.plan(obs, sensors, frame_at, now, ...) src/follow_control.py:292 def plan_visual_follow(...) # 无调用者 src/follow_control.py:320 def plan_follow(...) # 无调用者
工业做法
单一职责、单一实现；死代码即删，或用测试锁死唯一入口。
迁移动作
删除两个 plan_*，把现役规划抽成独立可测模块。
P1

持锁跨越规划计算 + 网络往返

camera_viewer.py:142-161

motion_lock 与 lock 嵌套，且 session.sent() 在另一分支再次取 lock。锁范围覆盖了规划与 IO，Web 端 /status 会被控制循环拖慢，反过来又加剧 HMI 卡顿。

工业做法
临界区只保护共享状态读写；计算与 IO 在锁外完成。
迁移动作
缩小临界区，快照式取值后在锁外计算。
P1

udev 命名漂移：laser vs lidar

lslidar_driver/params/lsx10.yaml

官方规则生成 /dev/wheeltec_laser，驱动参数也写 /dev/wheeltec_laser；本项目车端记录却是 /dev/wheeltec_lidar。名字不一致，换卡/重装即断链。

lslidar_driver/params/lsx10.yaml: serial_port_: /dev/wheeltec_laser lidar_name: N10 # 可选 N10_P 官方 udev: SYMLINK+="wheeltec_laser"
工业做法
单一命名真相源；部署脚本里做「符号链接存在性」断言。
迁移动作
全仓统一为 wheeltec_laser，部署时校验。
P1

启动脚本不检查失败，开机「假成功」

ops/robot-follow-boot.sh

set -u 但没有 -e；docker exec -d 不检查退出码；健康检查 timeout 25 ... || true。桥可能根本没起来，但开机流程照样走完，界面看起来正常。

set -u # 无 -e docker exec -d ... ${container} # 不检查返回值 timeout 25 python3 "$assets/boot_health.py" || true
工业做法
关键步骤失败即中止并显式报错；启动后做端到端就绪断言。
迁移动作
加 set -euo pipefail，校验每个 exec 的退出码。
P1

健康阈值与控制阈值不一致

ops/boot_health.py

监督层认为 1 s / 2 s 才算不健康，控制层 SCAN_TIMEOUT=0.4 / FRAME_TIMEOUT=0.5 早已降级。两套标准打架，导致「系统健康但功能已降级」的盲区。

工业做法
健康判定阈值从同一配置派生，单一定义。
迁移动作
把超时阈值收敛到一份配置，boot_health 复用之。
P1

monotonic 时间跨重启比较，退避逻辑失效

ops/boot_health.py

time.monotonic() 每次开机归零，却被持久化后与上次写入值比较。结果退避上限、故障计数在重启后全部失真。

工业做法
跨重启用 wall-clock 或持久化计数器 + boot_id 命名空间。
迁移动作
加 boot_id 校验，不同 boot 则重置计数。
P1

异常被吞成「等待数据」

camera_viewer.py:148

规划里任何异常都被 except Exception 兜住并转成 fault_paused，真相被掩盖；跟着出现的是反复重试而不是暴露根因。

:148 except Exception: :149 logging.getLogger(__name__).exception('Control update failed') :150 session._wait('fault_paused', '控制计算异常，等待有效传感器数据', now)
工业做法
区分「可恢复降级」与「致命故障」；致命故障进安全态并要求人工介入，而非静默重试。
迁移动作
按异常类型分流，致命类进维护态并告警。

7.3工程级（P2）

P2

CI 只跑测试，没有 lint / 类型 / ARM64

.github/workflows/ci.yml

矩阵是 ubuntu/windows × py3.11/3.12，只做 pytest + compileall + bash -n。没有 ruff/mypy/覆盖率，没有 colcon 构建 ros2_ws，没有 aarch64 目标——而车端恰恰是 aarch64。

工业做法
静态检查门禁 + 覆盖率阈值 + 与目标架构一致的构建/冒烟。
迁移动作
加 ruff/mypy/coverage；加 arm64 runner 或 qemu 构建。
P2

依赖锁在旧版本，无 SBOM

requirements/

ONNX Runtime 1.23.2 / NumPy 1.24.2 / SciPy 1.10.1 / Pillow 9.4.0。Pillow 9.4 属于较早版本线。仓库无 SBOM、无依赖签名校验、无 CVE 门禁。

工业做法
CycloneDX SBOM + 依赖哈希锁定 + 定期漏洞扫描。
迁移动作
生成 SBOM，接 Dependabot/OSV 扫描。
P2

模型与发布包无完整性校验

releases/ · ops/deploy-on-robot.sh

归档有 SHA-256（0554fe93…），但部署脚本未见校验；.onnx 模型无签名，可被替换。

工业做法
发布包与模型都签名（cosign / minisign），部署前校验。
迁移动作
部署脚本加 sha256sum -c 与签名校验。
P2

没有 OTA 与回滚

deploy-on-robot.sh

手工推送，备份目录手工创建（20261116-165035）。无 A/B 分区、无健康门控回滚。

工业做法
A/B 分区 + 健康检查失败自动回滚。
迁移动作
引入 rauc / swupdate 或等价方案。
P2

日志写容器 /tmp，重启即失

ops/robot-follow-boot.sh

诊断日志落在容器 /tmp/wheeltec-boot-*.log，容器重建即丢；无结构化日志、无指标导出、无追踪。

工业做法
结构化日志外送 + 指标（Prometheus）+ 分布式追踪。
迁移动作
日志落持久卷，加最小指标端点。
P2

时钟未统一，多传感器「同一时刻」是伪命题

全栈

相机、雷达、控制各自 time.monotonic()，无 PTP/chrony 精度说明，也无 message_filters.ApproximateTime 对齐。融合前提（同一时刻）实际未闭合。

工业做法
统一时基 + 硬件触发 + 时间同步策略。
迁移动作
启用 chrony/PTP，融合处用 message_filters。
P2

HMI 与控制同进程

camera_viewer.py

Flask Web 控制台与控制回路同一个 Python 进程。网页卡顿、被 CSRF、或渲染阻塞都会影响控制。VIEW_ONLY 还是一个模块级常量，没有运行时权限门。

:155 active = bool(session.armed and (forward or turn) and not VIEW_ONLY)
工业做法
HMI 与控制回路进程隔离；权限运行时可控且可审计。
迁移动作
拆出独立 HMI 进程，权限改为运行时配置。
P2

状态全在内存，崩溃即丢会话

follow_session · Restart=on-failure

跟随会话、跟踪器、相机状态全在进程内存，无 WAL、无快照。systemd Restart=on-failure 会静默重启，看起来「自己好了」，其实会话已重置。

工业做法
关键状态可恢复或显式声明「重启即安全态」。
迁移动作
重启后强制进安全态并告警，而非静默续跑。

7.4一句话总结

这套代码的功能完整度相当高——检测、跟踪、Re-ID、几何、限速、电压保护、HMI、发布都有，28 项测试也过了。它离工业的距离不在「会不会做」，而在「失败时会不会静默」：安全靠软件、凭据会外泄、异常会吞、启动会假装成功、时间不对齐。这些正是工业认证最先卡住的地方。

从「课堂演示能跑」到「可以交付给第三方在有人环境里运行」，中间要补的不是算法，是安全闭合、可观测、可回滚、可验证。按依赖顺序分 6 个阶段，前一阶段不验收不进入下一阶段。

P0安全闭合1 – 2 周
  • 硬件急停：独立双通道 E-stop 直接断动力，不经过 Pi 与容器（ISO 13849 PL c / Cat 2）。
  • 制动实测标定：斜坡试验测实际减速度，把 braking_verified 改为 true；未标定前压低速度上限。
  • 移除令牌泄漏：/status 不再返回 START_SESSION；关机改独立鉴权 + 二次确认 + 审计。
  • 控制路径去 IO：把 HTTP 移出控制回路，抖动硬上界压回 280 ms 预算内。
  • 验收：急停响应测量、制动距离表、/status 无敏感字段、看门狗抖动 < 100 ms。
P1架构归一2 – 4 周
  • 拆 HTTP 桥：传感器/执行器改原生 ROS2 节点，显式 QoS，message_filters 时间同步。
  • 删死代码：移除 follow_control.py:292/320 两个零调用规划器。
  • 生命周期：核心节点改 lifecycle node，状态机显式化。
  • 进程隔离：HMI 独立进程，权限运行时可控。
  • 验收：节点图可导出、QoS 有文档、无死代码、HMI 崩溃不影响控制。
P2可观测与测试2 – 4 周
  • 结构化日志 + 指标：日志落持久卷，暴露最小指标集（FPS、时延、看门狗、电压）。
  • 测试矩阵：把手册待做项变成自动化——0.15/0.20/0.25 分档、多人交叉、10 min 连续、30 cm 停车 20 次 ≥19、遮挡恢复 20 次 ≥19（1 s 内）。
  • CI 加码：ruff / mypy / coverage / colcon / arm64 冒烟。
  • 验收：测试报告可复现，CI 红灯即阻断。
P3时间与几何1 – 2 周
  • 统一时基：chrony / PTP，多传感器时间同步策略落地。
  • 几何工件化：外参从硬编码改为标定工件 + 校验脚本；udev 统一 wheeltec_laser。
  • 验收：时间同步误差有量化指标；换件后校准流程可执行。
P4发布与安全2 – 4 周
  • 供应链：CycloneDX SBOM + cosign 签名 + 依赖 CVE 门禁；模型签名。
  • OTA：A/B 分区 + 健康门控自动回滚。
  • 通信安全：DDS Security / mTLS。
  • 验收：断电回滚演练通过；发布包与模型校验可离线复现。
P5产品化持续
  • 参数 schema + 版本迁移；远程诊断通道与审计。
  • FMEA 文档；功能安全计划；供应链双源（尤其停产的相机）。
  • 验收：第三方按文档可部署、可诊断、可回滚。

8.2结语

这台车的硬件组合（麦轮 + 单线 TOF + 结构光 + Pi 5 + STM32 驱控一体）是教学场景下的合理选择：便宜、能跑、能讲清楚每个环节。真正要跨过的门槛，是把「演示能跑」升级成「失败可证」——从软件看门狗升级到物理急停，从 HTTP 桥升级到原生 ROS2，从手工部署升级到签名 + 回滚。P0 到 P1 的投入最小、收益最大，是性价比最高的起点。
