# ROS2 学习笔记 01 · 零基础第一篇

日期：2026-11-19
性质：**学习记录，不是本项目的实现说明。** 实现口径以 [架构说明](architecture.md) 和 [实施记录](IMPLEMENTATION.md) 为准。
讲解用的车体数字（如"雷达退后 0.10 米"）是为推算方便设的**示例值**，与实车标定值无关，不要当作标定依据。

---

## 一句话总纲

> ROS2 = **一堆只干一件事的小程序** + **三种说话方式** + **一张空间换算表** + **一套查问题的命令**。

ROS2 不提供任何算法：不做目标识别、不做路径规划、不做电机控制。你写的仍然是普通 Python，只是在数据的**进出口**换成 ROS2 的话术。

它也不是操作系统，不做硬实时，Windows/macOS 支持很弱。

---

## 骨架四块

### 1. 节点（Node）

一个节点 = 一个**独立运行的进程**，只负责一件事：管雷达的、管相机的、管电机的、做决策的。

关键性质是"独立进程"而不是"一个类"：崩了不连坐、能单独重启、能跑在另一台机器上。

类比：公司里的**岗位**。员工请假了岗位还在，招人填上就恢复。

### 2. 话题（Topic）+ 消息（Message）

对讲机模型，三要素：

| 要素 | 人话 | 例子 |
| --- | --- | --- |
| 频道名 | 这件事叫什么 | `/scan` |
| 表格类型 | 按哪张固定表格播报 | 雷达专用表格 |
| 谁喊 / 谁听 | 发布 / 订阅 | 雷达程序喊，你的程序听 |

最重要的性质：**话题是一条一直开着的水龙头。** 你订阅上的瞬间就会源源不断收到；没人喊就一直等，不报错，也不会收到"没有"这个答复。

发布方不认识订阅方，带来三个好处：

1. **加人不改老代码** —— 想加一个"把数据画到屏幕"或"再跑一个算法做对比"，直接收听即可。
2. **挂了不连坐** —— 收听方崩了，喊话方照常喊。
3. **两边可以分开造** —— 底盘是厂家做的，算法是你写的，只靠频道名对上。

### 3. TF 坐标系

车上每个传感器说"位置"时的参照物不一样：雷达说"离**我** 0.7 米"，相机说"**画面**中间偏左"，导航说"**客厅**东北角"。这些"我"不是同一个点。

TF 是一张自动维护的空间换算表，随时回答"雷达相对车身差多少、车身相对地图差多少"，并自动换算。

只要算法要回答"在我前面多远"，就一定绕不开 TF。

### 4. 查问题的命令

学会这几个就能自己诊断绝大部分毛病：列出所有频道、偷听某个频道、看它每秒喊几次、看某个节点在听什么喊什么、把 TF 画成一棵树、把整场对话录下来回放、把点云和画面画在一个窗口里。

这一层比多学任何概念都有用。

## 三种说话方式怎么选

> ⚠️ **不要看"这件事持续多久"**，时长从来不是判据。

看这两句：

| 自问 | 结论 |
| --- | --- |
| 有没有"**做完了 / 失败了 / 被取消了**"这个时刻？需不需要**你派它**才开始？ | **动作（Action）** |
| 不派活它也在自己流？ | **话题（Topic）** |
| 答案**必须现场执行才拿得到**？ | **服务（Service）** |

- **服务** = 问一句、站着等回信。适合几秒内就有结果的事。
- **动作** = 派一件要干一阵子的活，有三个洞：递进去的 `goal`、途中一直回的 `feedback`、结束时的 `result`，而且**随时能喊停**。这三样是动作独有的。

本项目的对照：相机画面是话题（拍到断电为止，永远不会"完成"）；"跟住那个人"是动作（会跟丢、会被人工取消）。

## TF 的三条硬道理

1. **一个距离数字不绑"方向"和"原点"就毫无意义。**
   雷达 360 度全扫，"最近障碍 0.25 米"完全可能是左后方的一条桌腿。所以 ROS2 的雷达消息除了距离，还额外带着"这批读数是相对哪个东西量的"和"每一束对应哪个角度"。
2. **净距 = 雷达读数 − 雷达退后量。**
   例：0.25 − 0.10 = 0.15 米。所以"30 厘米停车"必须说清指车头净距，不是雷达读数。差 10 厘米，车贴近墙时就是撞与不撞。
3. **算出负数就是警报**，意思是模型和现实不一致了。可能是：
   - 车头已经越过那个东西，也就是可能已经贴上；
   - 更常见的真相：**雷达看到的是自己的车壳、支架、扎带**（自遮挡），每台装雷达的车都踩过；
   - 太近了，落在雷达最小量程之外，读数已不可信；
   - 雷达只扫一根水平线：桌腿扫得到，悬空的桌面、地上的地毯、台阶都扫不到。

### 由负数推出来的三条保命设计

1. 不要全 360 度取最小值，**只认正前方一条走廊宽度以内**的点。
2. **不认孤零零一个读数**，要同一团点里好几束一起报才算有障碍。
3. 雷达说"前面没人"但相机里那个人越来越大 → **停下来等**，不赌雷达对。

## 一条安全原则

> **安全相关的东西，宁可重复广播，也不要指望一条消息被收到。**

"急停"不应该是一条发出去等回信的请求——那一条可能丢，你以为车停了其实没有。

正确做法：**不停地广播"速度 0"，一秒发二十次**，同时底盘侧设一个规矩：**超过 0.28 秒没收到新指令就自己停车**。丢三条也没关系，下一条 50 毫秒就到。

## 术语对照（人话 ↔ ROS2）

| 人话 | ROS2 术语 |
| --- | --- |
| 只干一件事的小程序 | 节点 Node |
| 频道 | 话题 Topic |
| 固定播报表格 | 消息类型 Message |
| 喊 / 听 | 发布 Publish / 订阅 Subscribe |
| 问一句等回信 | 服务 Service |
| 派活、能问进度、能喊停 | 动作 Action |
| 空间换算表 | TF |
| 岗位说明书 / 参数旋钮 | 参数 Parameter |

## 尚未学到 · 按挡路程度排序

**第一档（最挡路）**

1. 工作空间与包：`package.xml`、`setup.py`、`colcon build`、`source install/setup.bash`
   —— "会读别人代码"与"能自己造一个节点"之间的那道门，本项目目前没有这一层。
2. 话题命名、命名空间与重映射（remap）。
3. QoS 实用三项：可靠 vs 尽力而为、队列深度，以及一条要命的规律——**两边设置不兼容时不报错，只是安静地收不到数据**。
4. 参数系统：为什么改一个停车距离必须重启进程。
5. launch 文件：为什么不该靠手敲五个终端把车启动起来。

**第二档（很快会碰到）**

自定义消息（`.msg`/`.srv`/`.action`）、URDF（TF 那些数字的源头）、调试与录制回放工具、系统时间 vs 仿真时间、`ROS_DOMAIN_ID` 与容器网络（本项目的 ROS2 跑在 Docker 容器内，容器内外默认互相听不见，这一条格外重要）。

**第三档（现在别碰）**

执行器与回调组、多线程死锁、生命周期节点、Nav2 / SLAM / ros2_control 生态。

## 我的两个已纠正误区

1. ❌ 用"持续时长"区分动作和话题 → ✅ 用"有没有完成 / 失败 / 取消"。
2. ❌ 以为消息表格全部由 ROS 写死、不能改 → ✅ 官方给了常用的那几张，**留白部分要自己定义**。本项目"锁定 3 号人物、当前距离 1.2 米"这类信息官方没有现成表格，必须自己画。
